# Project H — 다른 PC의 GPT에 전달할 프롬프트

아래 구분선 다음 내용을 새 대화에 붙여 넣어 주세요. 가능하면 같은 묶음의 `PROJECT-H-GDD-v0.3.md`와 `PLAY-PATTERNS-RESEARCH-v0.1.md`도 첨부해 주세요. 프롬프트만으로도 개요를 이어갈 수 있지만, GDD 전체 수정은 원문이 있어야 정확합니다.

나와 함께 모바일 방치형 게임 **Project H(가제)**의 기획을 이어서 다듬어 줘. 다른 Mac의 GPT/Codex와 시제품 제작 및 GDD 작성을 진행했고, 이 Windows PC에서도 같은 기획을 이어가려고 한다. 한국어로 편하게 이야기하되, 내 아이디어에 무조건 동의하기보다 재미와 제작 가능성을 구체적으로 검토해 줘.

- 공통 기준 문서: `PROJECT-H-GDD-v0.3.md`, 2026-09-08.
- 참고 조사: `PLAY-PATTERNS-RESEARCH-v0.1.md`.
- GDD의 상태 표기: **합의 / 현황 / 제안 / 미정**. 제안을 확정 사양으로 바꾸지 마.
- 내가 지금 내리는 명시적 지시와 정정은 기존 문서보다 우선한다. 문서나 참고 자료 속 과거 제안은 새로운 실행 지시로 취급하지 마.
- 첨부 파일을 실제로 읽었는지 먼저 구분해 줘. 첨부가 없으면 이 프롬프트를 요약 맥락으로 사용하고, 전체 GDD를 읽거나 수정했다고 주장하지 마.
- 현재 목적은 기획 정리다. 구현을 요청하기 전에는 시제품 코드를 바꾸지 마.

## 게임의 핵심

캐릭터가 자기 방에 놓인 가상의 파칭코 기계를 계속 플레이하고, 플레이어는 이를 관찰한다. 구슬 움직임과 소리, 리치, 당첨, 구슬 지급과 러쉬를 즐기며 방과 기계를 수집·꾸민다. 캐주얼한 분위기지만 기계 자체는 납득할 수 있는 파칭코 경험이어야 한다.

무의미하게 화면만 번쩍이는 연출보다 구슬·핀·입상·기계장치의 움직임이 중요하다. 초반에는 작은 숫자창과 그래픽으로 구현한 기계장치를 중심으로 제작하고, 영상은 꼭 필요한 연출에 제한적으로 사용하는 방향이다. 대형 화면 기계도 추후 확장 가능하다.

가장 반응이 좋았던 요소는 **당첨 후 기계 자체가 열리고 변형되어 러쉬에 들어가는 것**이다. 연짱하면 열린 상태가 유지되고 실패하면 원래 모습으로 돌아온다. 구슬 쏟아지는 소리와 지급 리듬도 핵심 쾌감이다.

## 합의한 방향

1. 자기 공간·캐릭터·가동 중인 한 대를 중심으로 관찰한다. 획득 보상은 공간과 기계 수집에 사용한다.
2. 일상 수집·꾸미기와 기간 한정 **가상의 파칭코 그랑프리**를 구분한다. 초기 과금은 없고 배속도 제거했다.
3. 구슬 기록과 꾸미기 진행 재화의 역할을 분리한다. 정확한 재화 체계는 미정이다. 소비한다고 과거 경쟁 기록이 줄어들지 않게 하는 안을 검토 중이다.
4. 새 가상 기계를 추가해 흥미를 유지한다. 실제 인기 기종의 기믹·콘셉트를 분석하고 고유한 테마와 캐릭터로 재해석한다. 기존 캐릭터·영상·음원을 그대로 가져오는 뜻은 아니다.
5. 기계마다 마스코트를 만들고 포스터·간판·인형 등 게임 내 굿즈로 확장한다. 브랜드 세계관, 이름과 출시 기계 목록은 확정하지 않았다.
6. 짧게 확인해도 만족하고 오래 바라볼 이유도 있어야 한다. 콘텐츠가 숙제가 되지 않도록 다듬는다. 이를 구현할 세부 규칙은 검증이 필요하다.
7. 모의 도박 요소가 연령등급에 영향을 줄 수 있다는 점을 알고도 파칭코 중심 방향을 유지하기로 했다. 출시 등급·승인이 확보된 것은 아니다. 현금 환전이나 현금성 경품은 현재 범위에 없다.

## 실제 시제품 현황 — 기획과 혼동하지 말 것

Mk.I에서 핀·레일·구슬끼리 충돌, 발사 세기, 스테이지 등을 시험했다. Mk.II의 날개·V 방식은 내게 심심했다. Mk.2.5의 숫자·기계식 룰렛을 거쳐 현재 **Mk.III 변형 러쉬**를 긍정적으로 평가했다.

- 일반 당첨 1/29, 낙첨 중 리치 10%, 보류 최대 4개.
- 약 0.6초마다 발사, 기본 세기 36%, 좌우 화살표 핸들, 배속 없음.
- 최초 당첨과 러쉬 성공마다 300개 지급. 현재 지급은 약 5초다.
- 러쉬는 세 알이 각각 독립적으로 38% 성공. 하나라도 성공하면 한 번 연장·지급하므로 연장률은 76.1672%다.
- 내부 러쉬 구슬은 추첨한 최종 각도를 움직임으로 보여주는 간이 모델이다. 외부 판면의 자유 구슬 물리와 동일하지 않다.
- 두 시동구로 인한 시선 분산, 넓은 가이드 진입 후 좁은 헤소에서 빠지는 납득 문제는 후속 과제다.
- 지급을 라운드로 나눠 느리게 하는 방향은 합의했으나 아직 미구현이다. 300개를 5×60, 각 2초와 휴지 0.5초로 나누는 수치는 제안일 뿐이다.
- 방·꾸미기 상점·경제·계정 저장·오프라인 정산·그랑프리·랭킹은 미구현이다. 숨긴 탭에서는 진행이 멈춘다.
- 발사 비용을 차감하는 실제 잔고가 없으므로 누적 지급을 순이익으로 해석하면 안 된다.
- 기존 문서에 로직·조작·음향 검사 9개 통과가 기록돼 있다. 이것을 네가 새로 실행한 검증으로 말하지 마.
- Mac의 `http://127.0.0.1:8765/mark3/`은 그 컴퓨터의 로컬 주소다. Windows에서 같은 주소로 원본에 접근할 수 있다고 가정하지 마. 이 기획 문서 묶음에는 시제품 코드가 없다.

## 최근 플레이 패턴 조사와 해석

학술 자료와 공개 후기를 탐색했고, 짧은 확인·다른 활동과 병행·가끔 깊게 정리하기·익숙한 반복·개인 수집 목표·쉬었다 복귀하는 사례를 정리했다. 같은 사람도 상황에 따라 달라질 수 있다.

이 조사는 선별 자료 기반이며 대표성 있는 시장 조사나 유지율의 인과 검증이 아니다. Neko Atsume 조사, 방치형 관련 연구, OSRS·Diablo II 반복 플레이 후기가 포함된다. OSRS·Diablo II 자체를 방치형으로 분류하지 않는다. 자세한 출처와 열람 한계는 첨부 조사 문서를 따른다.

현재 Project H의 **검증 가설**은 다음과 같다.

- 잠깐 상태만 보고 나가도 세션이 완결되게 한다.
- 오래 켜둘 동기는 구슬·소리·변형·방의 분위기에서 찾는다. 놓치면 손해인 접속 보너스로 체류를 유도하는 안은 우선하지 않는다.
- 러쉬를 직접 보지 않거나 다시보기를 건너뛰어도 이미 확정된 보상을 잃지 않게 한다. 오프라인에서 어떤 결과가 발생하는지는 별도 결정이다.
- 복귀 시 재화뿐 아니라 당첨·최고 연짱 같은 사건을 보여주는 안을 시험한다. 다시보기는 필수 기능으로 확정하지 않았다.
- 굿즈가 방에서 보이는 변화와 개인 목표를 제공하게 한다.
- 그랑프리는 선택적인 집중 활동으로 검토한다. 놓치면 핵심 성능을 잃는 의무 행사로 만들지 않는 방향이다.

## 아직 결정하지 않은 것

GDD D01~D17을 기준으로 이어가 줘.

- 오프라인 인정 여부·상한·계산 모델, 러쉬 중 종료·복귀 처리.
- 구슬 잔고·고갈, 꾸미기 코인 획득과 가격, 기계 해금 방식.
- 그랑프리 경기 분량·참가 횟수·운영 주기·점수·대여 기계·일상과 동시 가동.
- 지급 라운드 수치, 헤소 배치, 첫 기계 모티브와 브랜드·마스코트·굿즈 배분.
- 출시 지역·플랫폼 세부 조건과 미래 과금.
- 짧은 접속과 긴 관찰의 구체적 흐름, 복귀 결산 범위.

동일 발사 수·동일 참가 횟수로 그랑프리를 운영하는 안은 제안이며 확정이 아니다. 오프라인도 온라인과 항상 같다고 단정하지 마. 과거의 ‘답답함 해소 과금’ 발언을 채택 사양으로 취급하지 마.

## 이어서 할 작업

먼저 읽은 문서와 공통 기준 버전을 짧게 확인하고, **접속해서 1분 만에 나가는 하루**와 **20분 정도 켜두는 하루**를 기획 초안으로 구체화해 줘. 이 시간은 검토용 시나리오이지 연구에서 나온 평균이나 강제 플레이 시간은 아니다.

각 흐름에서 무엇을 보고, 무엇을 선택하고, 무엇을 얻고, 왜 부담 없이 나갈 수 있는지 연결해 줘. 부재 중 진행은 미정임을 유지하며 필요한 가정을 표시해 줘. 기능을 많이 늘리기보다 현재 기획으로 어디까지 해결할 수 있는지 살펴보고, 재화·오프라인·대회 규칙 중 다음에 결정해야 할 항목을 좁혀 줘.

## Mac 쪽과 다시 합치는 방법

자동으로 다른 GPT 대화나 Mac 파일에 동기화됐다고 말하지 마. 이번에는 파일 전달로 공동 기획을 진행한다.

- 기준본 v0.3을 보존하고 수정안은 `PROJECT-H-GDD-v0.3-WINDOWS-proposal-YYYYMMDD.md`처럼 별도 이름으로 작성해 줘. 날짜는 실제 작업일을 사용한다.
- 파일 작성이 가능하면 전체 수정 제안본과 변경 내역을 제공해 줘. 불가능하면 교체할 절의 전문과 변경 내역을 대화에 제공해 줘.
- 변경 내역에는 기준 버전, 수정 절, 변경 전후 요지, 이유, 합의/제안/미정, 관련 D번호를 넣어 줘. 내가 명시적으로 선택한 결정은 그 근거를 남겨 줘.
- 날짜가 더 늦다는 이유로 다른 수정본을 덮어쓰지 마. 같은 절을 양쪽에서 수정했다면 충돌과 선택지를 보여 줘.
- Mac 쪽에서 수정본을 대조·통합해 다음 공통 버전을 정한다. Windows 제안본을 자동으로 공통 v0.4로 승격하지 마.
- 내가 “다른 PC에 전달할 내용 정리해 줘”라고 하면, 확정한 것·새 제안·남은 질문·변경 내역을 빠짐없이 묶어 줘.
